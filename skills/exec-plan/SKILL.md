# 执行

执行 `spec.md`，或对小而清晰的任务直接实现代码修改。

## 核心原则

- 优先做最小正确的变更。
- 有计划时按计划执行；无计划的小任务先形成简短内部执行备注，必要时向用户简述。
- 只为阻塞问题暂停；非阻塞不确定性记为"假设"并继续。
- **验证门（唯一硬性约束）**：未运行验证命令并亲自读取其新鲜输出前，不得宣称"测试通过/验证通过/任务完成"。不得基于记忆、假设或子 agent 自述下结论。跑命令，读输出，再下结论。不可商量。编译、lint、格式检查优先由构建插件或 CI 自动执行，主线程读取其新鲜结果；智力审查聚焦确定性工具无法证明的风险。
- 修改完成后须验证；无法验证时说明原因。
- 新增/删除/变更功能行为、重构或修复关键 bug 后，判断是否影响功能条目、核心实现或关键测试入口；仅在确认变化时进入 `route-sync`。
- **子 agent 按条件使用**（见下）：仅当任务独立可验证且无文件冲突时才并行派子 agent。
- 主线程负责子 agent 任务划分、集成、最终判断与交付。
- 任务目录存在时，任务过程中产生的相关产物（SQL、API 文档、测试报告、`plan-fix{n}.md`、`unresolved-issues.md`、评审报告 `review{n}.md` 等）归集到 `spec` 建立的任务工作区（`docs/routespec/yyyy-MM-dd-{spec_name}/`），便于跨会话回溯；无任务目录的小任务不落盘产物，在执行摘要中说明。
- 多代码库工作区中，改动哪个代码库，产物归哪个代码库的任务工作区；工作区根的跨库协作文件（collaboration.md）仅跨库任务由 `spec` 建立、由跨库开发者自行维护，本技能只读；单库任务不建该文件。
- 用户要求提交变更时，由开发者惯用的提交技能或常规 git 流程完成；存在任务目录时在提交信息中记录其位置。
- 实现完成后做一次任务复查，优先发现遗漏、回归风险与验证缺口。
- **评审子 agent 为可选**：行为变更、跨模块、鉴权与数据敏感改动在主线程验证门通过后启用 `code-reviewer`；typo、纯配置、纯文档不启用，其余改动按风险决定。评审带显式停止条件。
- **自评克制**：默认以一次任务复查收尾，不反复自评代码质量；评审只覆盖上述风险范围。避免重复 verify 绕圈子烧 token。

## 工作流程

1. 读上下文：
   - 任务目录存在时，读 `spec.md` 与最新 `plan-fix{n}.md`。跨库任务按涉及的库分别读各自任务目录（`spec_name` 跨库统一），并读各库 `docs/routespec/cross-repo/` 中与本任务相关的协同文档；改动不得违反在案契约，确需变更契约时同步更新各库对应协同文档。
   - `plan-fix{n}.md` 以编号最大者为最新；执行前检查 `spec.md` 与所有 `plan-fix*.md` 中的未结项——实际执行遵循最新修复计划与未闭合问题。
   - 从 `route-debug` 加载时，读其调试摘要（根因、分歧点、修复方向、受影响文件）作为执行备注。
   - 小直接改动读 `route-lookup` 结果与相关代码。
2. 读 `spec.md` 中的任务关系；无 `spec.md` 的小任务默认主线程执行，除非发现需拆分的复杂度。
3. 决定子 agent 使用方式（见下）。
4. 输出或维护简短任务清单，只覆盖本次修改与验证；小任务默认内部维护，除非用户需要或风险值得说明。
5. 执行代码修改，保持原风格，不投机性重构。
   - 新增逻辑时考虑先写失败测试以确认其能捕获问题，再实现使之通过；bug 修复尤其适用（先复现）。这是一条指引而非硬门——琐碎单行或纯机械改动可直接实现。
6. 运行相关验证：优先测试、类型检查、lint 或能证明改动正确的最小命令。
   - 验证门在此生效：跑命令、读新鲜输出、确认通过后再宣称成功。不信记忆、假设或子 agent 自述。
7. 任务复查：对照 `spec.md`、实际 diff 与验证结果，查遗漏、风险与测试缺口（见"任务复查"）。
8. 检查结果：
   - 通过：进入完成摘要。
   - 发现明确 bug 或遗漏（复查中发现）：直接修并再验证。
   - 多轮仍未解决：任务目录存在时写 `unresolved-issues.md`；无任务目录的小任务在摘要说明阻塞原因。
9. 判定 route-sync：`yes` / `no` / `uncertain`。确认功能条目、核心实现或关键测试入口变化时加载 `route-sync` 完成同步检查；为 `no` 时说明理由。跨库任务按涉及的库分别判定。
10. 用户要求提交变更时，按惯常提交流程完成（存在任务目录时提交信息记录其位置）；用户未要求提交时不主动提交。

## 子 agent 使用规则

先判断是否需要子 agent：

- 仅当任务"独立可验证 + 无文件冲突"时才并行派子 agent。
- 强相关/串行任务（共享核心文件、顺序依赖）由主线程直接做，或合并给同一子 agent 串行执行。
- 复杂或大范围改动即使无正式 `spec.md`，也可酌情用子 agent。
- 小而局部、单文件、低风险、无计划的任务可跳过子 agent。

再按相关性分组与排序：

- 强相关任务合并给同一子 agent，避免上下文碎片；合并后因文件冲突或依赖须串行时，子 agent 按正确顺序串行执行。
- 弱相关任务可按文件范围、功能链或验证入口合并，减少子 agent 数量与集成成本。
- 独立可验证的复杂任务优先拆给不同子 agent 并行。
- 冲突风险任务不得并行编辑同一文件；交给单个子 agent 串行，主线程事后审 diff。
- 探索、实现、补测试、评审可拆分；但同一行为链的实现与测试通常合并，除非测试边界完全独立。
- 评审固定使用只读的 `code-reviewer`，修复是独立角色；承担某轮审查的子 agent 不得修复该轮发现的问题。
- 修复子 agent 仅承接评审报告已给出位置与修法的机械修复，不得扩大范围或改变方案；主线程必须审查其 diff，验证门始终归主线程。

子 agent 任务须含明确输入文件、修改范围、禁区、预期产出与验证方式。子 agent 只负责探索、局部实现、补测试、验证或评审建议；主线程须审其结果、处理集成冲突、跑最终验证并承担最终交付。

## 任务复查

实现与验证后做一次复查，分两阶段：先 spec 一致性，后代码质量。

### 阶段一：spec 一致性

阶段二前必须完成。

1. 需求覆盖：`spec.md` 中每个任务是否完成；未完成是否有明确理由。
2. 行为风险：是否引入计划外行为变更、边界遗漏、兼容性问题或错误处理缺口。
3. 路由图影响：是否涉及需 `route-sync` 的功能条目、核心实现或关键测试入口。

### 阶段二：代码质量

阶段一通过后进行。

4. 代码范围：是否改了无关文件、是否投机性重构、是否动了用户既有无关改动。
5. 验证充分性：测试/类型检查/lint/人工验证是否覆盖当前风险；无法验证的理由是否可信。验证门须已通过——须有新鲜命令输出。

### 评审子 agent（可选，带停止条件）

默认做主线程单次自检；行为变更、跨模块、鉴权与数据敏感改动启用 `code-reviewer`，typo、纯配置、纯文档不启用。评审在主线程完成阶段一、阶段二且验证门通过后进行：

1. **派发输入**：每次派发必须附完整三件套，缺项先补齐：
   - 需求画像：目标 / 范围内 / 范围外 / 预期行为 / 设计约束；有 `spec.md` 时连同方案与风险自查结论提供。
   - 改动范围：实际 git diff 或完整文件清单，必须包含新增文件。
   - 验证状态：主线程已运行并通过的编译、单测与按需冒烟及其新鲜输出摘要。
2. **职责隔离**：`code-reviewer` 只读审查静态风险与测试有效性，不修文件、不跑编译或测试。修复权与验证门归主线程；修复子 agent 只承担报告已给出位置与修法的机械修复，且其 diff 由主线程审查。承担某轮审查的子 agent 不得修复该轮发现的问题。
3. **划片**：跨库任务按库各派一个 `code-reviewer`；同库多代理并行时按模块或风险面划片（安全 / 并发 / 契约文档 / 测试有效性），每片均附三件套与负责边界，避免重复扫描同一区域。
4. **报告**：按 `[Critical]` / `[Important]` / `[Minor]` 分级，每条附 `文件:行号`、问题与建议修复方式。任务目录存在时，主线程将报告保存为 `review{n}.md`；无任务目录时在摘要记录评审结论。
5. **停止条件**：默认 1 轮；仅出现 Critical 时，在其修复后对修复 diff 追加第 2 轮增量审查。第 2 轮不再循环，遗留问题按分级处置与范围升级规则处理。

发现确认问题时按「评审发现处置」处理；仅当存在方案遗漏、未达验收标准、明确回归风险或需单独跟踪的测试缺口时才生成 `plan-fix{n}.md`。

### 评审发现处置

1. **甄别归并**：主线程去重、排除误报、按严重度取舍，形成实际修复队列；不修项记录理由。原始发现数量不等于修复任务数量。
2. **分组修复**：按文件或模块分组，同组问题一次修改、一次相关验证，不逐条串行修复。
3. **增量验证**：每组修复后运行该组相关测试；全部修复后由主线程执行一次完整相关验证兜底。
4. **分级语义**：
   - Critical：必须修复；修复后验证并对修复 diff 做一次增量二轮审查。
   - Important：当轮修复；确有阻塞不能修复时记录为未决问题，不得宣称完成。
   - Minor：可延后，记录后不阻塞完成，不追加审查轮次。

### 评审红线

- spec 一致性未确认就开始代码质量评审。
- 因"改动简单"跳过复查。
- 不读新鲜输出就采信子 agent 的验证自述。
- 不经主线程审查就接受评审结论。
- 带 Critical 或 Important 未决就宣布完成。

## 范围升级

执行中发现改动范围显著超出预期（涉及新模块、新架构、跨文件行为变更），或单个审查报告超过 15 项、多个审查报告汇总超过 30 项时，视为任务粒度失控信号：

1. 暂停当前执行。
2. 向用户说明升级理由：原预期影响范围 vs 实际发现的影响范围；评审数量触发时附上归并前的分布概况。
3. 建议先加载 `spec` 拆分任务、确认方案，再继续，避免持续扩大修复范围。

小幅波动（多改 1-2 文件、加边界处理）无需升级——直接执行并说明。

## 修复计划规则

- 仅当存在 `spec.md` 且发现方案遗漏、未达验收、明确回归风险或测试缺口时才生成 `plan-fix{n}.md`。
- `plan-fix{n}.md` 须引用 `spec.md` 中稳定任务 ID；新修复任务可用 `F1`、`F2` 等。
- 小任务通常不生成修复计划——直接修并在摘要说明。
- 修复上限默认 3 轮。用户可用"放宽修复上限"或指定数量覆盖默认。任务目录存在时记入 `unresolved-issues.md`；无任务目录的小任务在摘要记录。

## 完成清单

完成前确认：

- 计划或执行备注中的任务已完成，或未完成理由清晰列出。
- 任务目录存在时，`spec.md` 或最新 `plan-fix{n}.md` 中的任务完成状态已维护。
- 已按复杂度判定子 agent 使用，按相关性分组完成，所有子 agent 结果已审查。
- 任务复查完成：阶段一通过，阶段二通过；行为变更、跨模块、鉴权与数据敏感改动已启用 `code-reviewer`，且三件套齐全、报告已归档或记录、结论已由主线程审查。
- **验证门已通过**：运行了验证命令、读了新鲜输出、确认成功。无基于记忆/假设/子 agent 自述的完成宣称。
- 评审发现已甄别归并、按模块分组修复并逐组复验；Critical 与 Important 无未决项，Critical 修复 diff 已完成增量二轮审查，Minor 延后项已记录。
- 已运行相关验证，或说明了未运行的理由。
- 已判定是否需要 `route-sync`；为 `yes` 或 `uncertain` 时已加载 `route-sync` 完成同步检查。
- 若执行了 route-sync，最终摘要含实际同步结果与修改的路由图文件；未能完成时说明原因或未确认内容。
- 用户要求提交时已完成提交，且提交信息记录了任务目录位置。
- 未改无关文件，未回退用户既有改动。

## 输出格式

```md
# 执行摘要

## 结果
- 完成 / 部分完成 / 未完成

## 改动文件
- `path/to/file`：修改说明

## 验证
- 命令：...
- 结果：通过 / 失败 / 未运行（理由）
- 验证门：通过（已确认新鲜输出）/ 未通过 / 不适用（理由）

## 执行策略
- 子 agent 使用：计划执行按需使用 / 未用（小任务无计划）
- 任务分组：无 / ...

## 任务复查
- 复查阶段：阶段一（spec 一致性）完成 / 阶段二（代码质量）完成
- 结论：通过 / 发现问题并修复 / 仍有问题
- 评审：未启用（理由）/ 已启用；轮次、报告位置与分级处置结果
- 顾虑：...

## RouteSync
- 需要 route-sync：是 / 否 / 不确定
- 受影响功能：...
- 同步结果：未执行 / 已更新 / 无需更新 / 部分 / 不确定 / 失败（理由）
- 路由图文件：无 / `docs/routespec/...`

## 提交
- 未提交（用户未要求）/ 已提交：{提交信息摘要，含任务目录位置} / 失败（理由）

## 遗留问题
- 无 / ...
```

## 反模式

| 借口 | 现实 |
|---|---|
| "改动很小，不必验证" | 小改动引发大故障。配置键的 typo、错误的 import 路径——都能靠跑验证抓住。 |
| "测试通过"（凭记忆/上次运行） | 记忆不可靠。验证门要求新鲜命令输出。跑命令，读输出，再下结论。 |
| "子 agent 说测试通过了" | 子 agent 自述不是验证。主线程须直接读新鲜测试输出。 |
| "我确信改动正确" | 信心不是证据。跑验证命令、读输出。 |
| "这不复杂，跳过评审子 agent" | 高风险/跨模块改动总能从第二眼受益。评审子 agent 抓实现者写完代码后看不到的遗漏与回归。（注意：默认单次自检已够，仅高风险/跨模块启用。） |
| "计划里已经内建评审了" | 计划阶段评审（设计期）与代码评审（实现期）抓不同类问题。都需要。 |
| "顺手重构一下这个" | 投机性重构有引入新 bug、扩大范围、搅浑评审的风险。只做计划内的改动。 |
| "稍后补测试，先把修复做完" | 除非改动琐碎或纯机械，否则你没确认测试能抓到原问题。先写失败测试再修。 |
| "route-sync 等等再说" | 拖延同步 = 路由图过期 = 下个任务定位更慢。趁上下文新鲜现在做。 |

# 路由查询

根据用户当前任务查询路由 wiki，快速判断应优先阅读哪些代码与契约文档。

## 核心原则

- 路由 wiki 优先于全仓搜索。
- wiki 是指针网络，不是知识库：只回答"用户提到的词汇与哪些代码、契约相关"。业务场景、架构场景、代码场景（含代码标识符）任一角度的词汇都应能命中。
- 唯一入口 `docs/routespec/wiki/index.md`，一次读取完成定位；命中后按需开 1-3 个路由页。页面只给起步阅读点——读到核心源码后沿代码依赖自然扩散，不要求图内穷举。
- wiki 存在但无匹配、显得过时或覆盖不足时，允许有针对性地扫描代码，但结果须标注为临时。
- 无法确认的功能或文件归属，标注为 `uncertain`。
- 本技能只向 `log.md` 追加 miss 行，不改动其他 wiki 文件。
- 用户只是询问代码问题、风险、实现逻辑、审查意见或诊断方向时，查询只为定位优先文件，不应直接进入修改、方案或执行流程。
- bug 报告与测试失败建议进入 `route-debug`，而非直接进入 `exec-plan`——定位根因应先于任何修复尝试。
- 需求澄清优先于执行：除小而明确的修改（typo、格式、依赖升级、纯文档、已定位且低风险的局部行为调整、用户已给出完整明确指令的机械修改）外，编码与修复任务在移交下游技能前先做需求澄清，收敛需求画像（目标、范围、边界、预期行为、约束）。需求澄清与 `spec` 的方案级阻塞问题职责分离：前者管"做什么 / 为什么"，后者管"怎么做"。

## 工作流程

1. 读 `docs/routespec/wiki/index.md`。
   - 不存在而 `docs/routespec/feature-routes/README.md` 或 `docs/routespec/feature-routes.md` 存在（遗留结构）：按旧结构继续查询——入口为其 README（内联形态直接匹配条目；索引形态先读"业务域 → 路由文件"映射再读域文件），覆盖状态标 `partial`，并在任务完成后建议按 `route-sync` 的迁移指南收敛。
   - 都不存在且当前任务需要代码定位：建议加载 `route-sync` 的"首次创建"模式完成初始化；初始化后回到本技能继续查询，覆盖状态记为 `partial`。
2. 语义匹配：以用户词汇——业务说法、架构说法、代码标识符、报错中的类名或文件名——对照 index 每行的页面名、一句话与关键词；直接命中与疑似命中一并列为候选。
3. 命中处理：打开候选中最多 2 个路由页，取得起步信息：
   - `核心`：优先阅读的源码文件。
   - `契约`：任务触及对应约束面（跨端行为、数据格式、对外接口、模块边界等）时，先读所指 `docs/integration/` 文档再动代码。
   - `相关`：仍不确定时顺链再开一页（含相关链累计不超过 3 页）；仍不确定即转扫描。
4. 未命中或不确定时进行有针对性扫描，优先源码、入口、配置与测试目录；排除依赖、构建产物、缓存与生成代码。经扫描确认定位后，向 `docs/routespec/wiki/log.md` 追加一行 miss 记录（文件不存在则创建）：
   `[yyyy-MM-dd] miss | "{用户词汇}" | resolved→[[{页面名}]] / unresolved`
   已有页面承接时 resolved 指向该页（供别名回填）；无页面承接时标 unresolved。
5. 判定覆盖状态：
   - `sufficient`：经 index 命中页面，核心文件与触及的契约均可定位。
   - `partial`：依赖扫描补齐定位，或命中信息缺失、显得过时。
   - `missing`：wiki 存在但无相关页面（含 unresolved 的 miss）。
6. miss 回填建议：经扫描确认定位且已有页面承接的词汇，在查询结果中建议任务完成后由 `route-sync` 补进该页 `别名`；unresolved 的词汇建议建页或并入近义页。
7. 判定任务意图与类型：
   - 分析任务：用户只是询问代码问题、风险、实现逻辑、审查意见或诊断。查询后读优先文件直接作答；不加载 `spec` 或 `exec-plan`。
   - 执行任务：用户明确要求编码、修改、新增、删除、重构或补测试。不含 bug 或测试失败报告（那些属于修复任务）。纯提交请求不属于执行任务——直接按惯常提交流程完成，存在任务目录时在提交信息中记录其位置。
   - 修复任务：用户明确报告 bug、测试失败、崩溃、回归或异常行为并希望修复。查询后建议加载 `route-debug` 做根因分析；在理解根因前不要跳到 `exec-plan` 或写修复。
   - 意图不明时按分析任务处理——先给出发现与建议，不主动改代码。修复与功能变更拿不准时，按修复任务处理，确保先理解根因。
8. 对（非修复的）执行任务，先判定是否属于可豁免需求澄清的"小而明确"修改：
   - 小而明确的修改（修 typo、调格式、升级依赖版本、纯文档、已定位且低风险的局部行为调整、用户已给出完整明确指令的机械修改）→ 直接进入 `exec-plan`，不经需求澄清。
   - 其余执行任务（不涉及功能变更的大范围改动、中大型、范围不清或需要确认方案的功能变更、拿不准者）→ 先进入第 9 步需求澄清，再据澄清结论分流。
9. 需求澄清（非豁免任务的硬性前置）：
    - 适用对象：第 8 步未判为小而明确的执行任务、修复任务，以及分析任务中用户问题本身不够具体者；分析任务中问题足够具体者直接作答。
    - 一次性提出当前所有待澄清点（可合并的合并为一组），每点附 2-3 个参考选项或标为开放问题；效率优先，不强制一次只问一个。收到回答后检查是否浮现新问题、冲突或矛盾需求；有则进入下一轮，无则收敛。
    - 收敛标志（满足其一即结束）：(a) 不再有待澄清点、新问题、冲突或矛盾需求；(b) 用户要求停止（如"别问了直接做"、"够了"、"先按你理解来"）。
    - 澄清产出随查询结果一并移交下游：需求画像（目标 / 范围 / 边界 / 预期行为 / 约束）交给 `spec` 或 `exec-plan`，避免下游重复提问。
    - 澄清阶段不改代码、不进入方案细节；方案级问题（实现方向、技术选型、拆解）留给 `spec`。
10. 澄清后分流（基于第 9 步的需求画像确认下游）：
    - 澄清后需求画像收敛、仍属小而明确的低风险改动 → 建议加载 `exec-plan`（需求画像随查询结果移交）。
    - 不涉及功能变更的大范围改动（重构、性能优化、技术栈/框架替换）→ 建议加载 `spec`。
    - 中大型、范围不清或需要确认方案的功能变更（新增/修改/删除功能行为）→ 建议加载 `spec`。
    - 修复任务（含澄清后确认为修复诉求者）→ 建议加载 `route-debug`（需求画像随查询结果移交）。
    - 分析任务 → 澄清后读优先文件直接作答，不进入执行类下游。
    - 拿不准时按需加载 `spec` 处理。
11. 路由 wiki 联动：
    - 覆盖为 `partial` 或 `missing` 时，任务完成后建议进行 `route-sync`；仅当本次任务确认改变了页面锚定的核心实现或契约时才更新 wiki。
    - 对 typo、格式、纯文档、依赖升级等不产生定位价值的任务，可判定 `route-sync` 为 `no`，但需说明理由。

## 内部判断清单

查询完成后，模型应内部明确以下判断以决定后续：

- 命中页面及其来源（index / 扫描 / 不确定）
- 用户词汇与页面的匹配依据
- 应优先阅读的文件及理由
- 涉及的契约文档：无 / `docs/integration/...`
- 可能相关或可能需要改动的文件，带来源标记
- 覆盖状态：`sufficient` / `partial` / `missing`
- 任务意图：`分析` / `执行` / `修复`
- 任务类型（执行与修复任务）：`功能变更` / `修复` / `重构` / `小改` / `不确定`
- 是否涉及功能变更（仅执行意图）：`是` / `否` / `不确定`
- 建议的下一个技能：`无` / `spec` / `route-debug` / `exec-plan` / `route-sync（首次创建）`
- 需求画像清晰度：`清晰` / `部分清晰` / `模糊` / `豁免`
- 需求澄清状态：`未开始` / `进行中` / `已收敛` / `用户喊停` / `豁免`

不为追求完整而扩大扫描范围。

## 标准输出格式

查询完成后，若后续技能需要读取本技能结果，按以下格式输出或记录：

```md
# 路由查询结果

## 命中页面
- [[page]]（来源：index / 扫描 / 不确定）：用户词汇「...」→ 匹配理由

## 优先文件
- `path/to/file`（来源：路由 wiki / 扫描 / 不确定）：优先阅读理由

## 涉及契约
- 无 / `docs/integration/{name}.md`：触及理由

## 可能相关或需改动文件
- `path/to/file`（来源：路由 wiki / 扫描 / 不确定）：相关性或潜在改动理由

## 覆盖
- 状态：sufficient / partial / missing
- 是否使用临时扫描：是 / 否

## miss 回填建议
- 无 / [[page]] ← "{词汇}" / unresolved："{词汇}"（建议建页或并入近义页）

## 任务分类
- 意图：分析 / 执行 / 修复
- 任务类型：功能变更 / 修复 / 重构 / 小改 / 不确定
- 功能变更（仅执行）：是 / 否 / 不确定
- 需要 route-sync：是 / 否 / 不确定

## 需求画像
- 目标：...
- 范围内：...
- 范围外：...
- 预期行为 / 约束：...
- 待解冲突：无 / ...
- 澄清状态：已收敛 / 用户喊停 / 豁免（理由）

## 确定的下一步
→ {动作}（之一：加载 route-debug / 加载 spec / 加载 exec-plan / 加载 route-sync（首次创建）/ 直接作答）
```

## 反模式

| 借口 | 现实 |
|---|---|
| "不用 wiki 我也能找到" | wiki 给出确切入口，跳过不必要的全仓搜索，更快更准。 |
| "这任务太简单，不必查询" | 即便是单文件改动，也受益于知道哪个是入口、哪些是下游依赖。 |
| "页面里没写实现细节，信息不够" | 页面是指针：细节在代码与契约文档。按 `核心` 读代码，触及约束面读契约。 |
| "wiki 可能过时，我直接搜" | 读 index 只需几秒。若过时，标 `partial`、扫描、记 miss，事后再用 route-sync 更新。 |
| "扫描找到了，不用记 miss" | 确认定位后记 miss，词汇回填进页面别名，下次同词经 index 直达。 |
| "我对代码库已经很熟" | wiki 跨会话持久。它帮下一个 agent（或未来的你）立刻跳到正确文件。 |
| "用户说得够清楚了，直接执行" | 表面清楚的需求常藏范围缺口与冲突预期。除琐碎任务外，先过需求澄清门；用户喊停才停。 |
| "需求澄清和 spec 问的问题一样，省了" | 澄清门问"做什么 / 为什么"，spec 问"怎么做"。职责分离，前者收敛后后者才聚焦方案，不重复。 |

## 首次初始化

当路由 wiki 不存在（`docs/routespec/wiki/index.md` 不存在，且无 `feature-routes` 遗留结构）且当前任务需要代码定位时，建议加载 `route-sync` 的"首次创建"模式完成初始建立。初始化完成后，继续本技能的查询流程，覆盖状态记为 `partial`。当 wiki 存在但无相关页面时，不创建页面——以 `missing` 覆盖状态进行有针对性扫描并记 miss，在任务完成后检查 `route-sync`。

## 相关技能

- `route-sync`：路由 wiki 与契约文档的养护（首次创建、日常同步、自检、迁移）。wiki 不存在时用其"首次创建"模式。
- `route-debug`：bug / 测试失败 / 异常行为的系统化根因定位。
- `spec`：中大型或范围不清任务的方向确认与可执行拆解。
- `exec-plan`：执行变更，以"验证门（跑命令读新鲜输出）"为硬性完成依据。

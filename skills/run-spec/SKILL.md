# 执行

执行 `spec.md`，实现其中的任务切片。

## 核心原则

- 优先做最小正确的变更，按 `spec.md` 及其修复计划执行。
- 只为阻塞问题暂停；非阻塞不确定性记为"假设"并继续。
- **验证门（唯一硬性约束）**：未运行验证命令并亲自读取其新鲜输出前，不得宣称"测试通过/验证通过/任务完成"；不得基于记忆、假设或子 agent 自述下结论。编译、lint、格式检查优先由构建插件或 CI 自动执行，主线程读取其新鲜结果，智力审查聚焦确定性工具无法证明的风险。
- 修改完成后须验证；无法验证时说明原因。
- 新增/删除/变更功能行为、重构或修复关键 bug 后，判断是否影响路由页锚定的核心实现或契约；确认变化时进入 `route-sync`。
- 在案契约（`docs/integration/`）是约束基准：触及契约先读对应文档；改动不得违反在案契约；契约与代码不一致时停下交用户裁决——改代码回归契约或显式修订契约，不静默偏移。
- 子 agent 仅当"独立可验证 + 无文件冲突"时并行派发；主线程负责任务划分、集成、最终判断与交付。
- 任务产物（SQL、API 文档、测试报告、`plan-fix{n}.md`、`unresolved-issues.md`、`review{n}.md` 等）归集到 `spec` 建立的任务目录（`docs/routespec/yyyy-MM-dd-{spec_name}/`）。
- 实现完成后做一次任务复查，评审子 agent 按风险启用（见"评审子 agent"）；默认单次自检收尾，不反复自评。
- 用户要求提交变更时由惯常提交流程完成，提交信息记录任务目录位置；未要求不主动提交。

## 工作流程

1. 读上下文：`spec.md` 与最新 `plan-fix{n}.md`（编号最大者为最新；执行前检查 `spec.md` 与所有 `plan-fix*.md` 的未结项，遵循最新修复计划与未闭合问题）；「RouteSync 与契约影响」标注契约时先读对应 `docs/integration/` 文档。
2. 读 `spec.md` 中的任务关系，决定子 agent 使用方式（见下）；维护简短任务清单，只覆盖本次修改与验证。
3. 执行代码修改，保持原风格，不投机性重构；新增逻辑与 bug 修复优先先写失败测试确认能捕获问题（指引而非硬门，琐碎或纯机械改动可直接实现）。
4. 运行相关验证：优先测试、类型检查、lint 或能证明改动正确的最小命令——验证门在此生效。中小范围的独立模块改动按改动面定向选择用例执行（按测试文件或用例名过滤），避免全量执行；跨模块、大范围或提交前的验证才跑全量。
5. 任务复查（见下）；发现明确 bug 或遗漏直接修并再验证；多轮仍未解决写 `unresolved-issues.md`。
6. 维护 `spec.md` 或最新 `plan-fix{n}.md` 中的任务完成状态。
7. 判定 route-sync：确认页面锚定的核心实现或契约变化时加载 `route-sync`；为「否」时说明理由。
8. 输出执行摘要；用户要求提交时按惯常流程完成。

## 子 agent 使用

- 强相关/串行任务（共享核心文件、顺序依赖）主线程直接做，或合并给同一子 agent 按序执行；独立可验证的复杂任务拆给不同子 agent 并行；冲突风险任务交给单个子 agent 串行，主线程事后审 diff。
- 同一行为链的实现与测试通常合并；探索、实现、补测试、评审可拆分。
- 子 agent 任务须含明确输入文件、修改范围、禁区、预期产出与验证方式；主线程须审其结果、处理集成冲突、跑最终验证并承担最终交付。

## 任务复查

先 spec 一致性，后代码质量；阶段一不通过不进阶段二。

- 阶段一（spec 一致性）：需求覆盖（每个任务完成或有明确理由）；行为风险（计划外行为变更、边界遗漏、兼容性、错误处理缺口）；路由 wiki 影响；契约一致性（与在案契约逐条不冲突，判定修订契约的已先行更新）。
- 阶段二（代码质量）：代码范围（无关文件、投机性重构、用户既有无关改动）；验证充分性（验证门已通过，有新鲜命令输出）。

## 评审子 agent

启用条件按 `spec.md` 的「验证与评审计划」执行；无计划或计划未覆盖时按风险判定：行为变更、跨模块、鉴权与数据敏感启用 `code-reviewer`，typo、纯配置、纯文档不启用。评审在任务复查两阶段完成且验证门通过后进行：

1. **派发内容**（缺检查范围时先补齐）：① 检查范围——本次改动文件清单或实际 git diff（含新增文件）；② 任务上下文——需求要点、设计约束、目标执行环境（如有）、需参考的契约与规范（`docs/integration/` 路径，无则写「无」）；③ 特别注意——执行者已确认的已知事实与需重点盯防的面（无则写「无」）。审查边界、报告范围与纪律由 `code-reviewer` 自身的系统提示词定义，派发时不重复、不添加角色或职责描述。
2. **职责隔离**：修复权与验证门归主线程。承担某轮审查的子 agent 不得修复该轮发现；修复子 agent 仅承接报告已给出位置与修法的机械修复，其 diff 由主线程审查。
3. **划片**：多代理并行审查时按模块或风险面划片（安全 / 并发 / 契约一致性 / 资源与错误路径），每片附派发内容与负责边界。
4. **报告与轮次**：按 `[Critical]` / `[Important]` / `[Minor]` 分级，每条附 `文件:行号`、问题与建议修复方式，保存为 `review{n}.md`。默认 1 轮；仅 Critical 修复后对修复 diff 追加一轮增量审查，不再循环。

### 评审发现处置

1. 甄别归并：主线程去重、排除误报、按严重度取舍形成修复队列；不修项记录理由。
2. 分组修复：按文件或模块分组，同组一次修改、一次相关验证；全部修复后主线程做一次完整相关验证兜底。
3. 分级语义：Critical 必须修复，修复后按上节做增量二轮审查；Important 当轮修复，确有阻塞不能修复时记为未决问题，不得宣称完成；Minor 可延后，记录不阻塞，不追加审查轮次。

### 评审红线

- 带 Critical 或 Important 未决就宣布完成。
- 未经主线程审查就接受评审结论或修复 diff。
- 不读新鲜输出就采信任何验证自述。

## 范围升级

执行中发现改动范围显著超出预期（新模块、新架构、跨文件行为变更），或单个审查报告超 15 项、多报告汇总超 30 项时：暂停执行，向用户说明原预期与实际影响范围（评审数量触发时附归并前分布），建议先加载 `spec` 拆分确认方案再继续。小幅波动（多改 1-2 文件、加边界处理）直接执行并说明。

## 修复计划规则

- 仅当发现方案遗漏、未达验收、明确回归风险或测试缺口时生成 `plan-fix{n}.md`；须引用 `spec.md` 稳定任务 ID，新修复任务用 `F1`、`F2`。
- 修复上限默认 3 轮，用户可用"放宽修复上限"或指定数量覆盖；未决问题记入 `unresolved-issues.md`。

## 完成清单

- 验证门已通过（新鲜输出在案）。
- `spec.md` / 最新 `plan-fix{n}.md` 任务完成状态已维护；Critical 与 Important 无未决，Critical 修复 diff 已完成增量二轮审查，Minor 延后项已记录。
- 在案契约无一违反，或冲突已交用户裁决并有结论。
- route-sync 与契约影响已判定；为「是」或「不确定」时已执行，摘要含实际同步结果与修改的 wiki 与契约文件。
- 用户要求提交时已完成，提交信息记录任务目录位置；未改无关文件，未回退用户既有改动。

## 输出格式

```md
# 执行摘要

## 结果
- 完成 / 部分完成 / 未完成

## 改动文件
- `path/to/file`：修改说明

## 验证
- 命令：...
- 结果：通过 / 失败 / 未运行（理由）
- 验证门：通过（已确认新鲜输出）/ 未通过 / 不适用（理由）

## 任务复查
- 阶段一（spec 一致性）/ 阶段二（代码质量）：完成情况
- 评审：未启用（理由）/ 已启用；轮次、报告位置与分级处置结果
- 顾虑：...

## RouteSync 与契约
- 需要 route-sync：是 / 否 / 不确定
- 受影响页面：...
- 契约：无涉及 / 已遵守 / 已修订（先契约后代码）/ 冲突待裁决
- 同步结果：未执行 / 已更新 / 无需更新 / 部分 / 不确定 / 失败（理由）
- 路由 wiki 文件：无 / `docs/routespec/wiki/...`

## 提交
- 未提交（用户未要求）/ 已提交：{提交信息摘要，含任务目录位置} / 失败（理由）

## 遗留问题
- 无 / ...
```

## 反模式

| 借口 | 现实 |
|---|---|
| "改动很小，不必验证" / "测试通过"（凭记忆或子 agent 自述） | 配置键 typo、错误 import 都能靠跑验证抓住；验证门只认新鲜命令输出。 |
| "顺手重构一下这个" | 投机性重构引入新 bug、扩大范围、搅浑评审。只做计划内改动。 |
| "稍后补测试，先把修复做完" | 除非改动琐碎或纯机械，先写失败测试确认能抓到原问题再修。 |
| "route-sync 等等再说" | 拖延同步 = wiki 过期 = 下个任务定位更慢。趁上下文新鲜现在做。 |
| "契约过时了，直接改代码" | 契约是约束真相，静默偏移制造多端漂移。先修订契约或交用户裁决。 |

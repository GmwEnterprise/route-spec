# 方案

把需求或已确认方向转化为清晰方案与可执行拆解，不直接写代码。

## 核心原则

- **阻塞问题聚焦方案层**：进入 spec 时先确认 `route-lookup` 是否已交付需求画像（目标 / 范围 / 边界 / 预期行为 / 约束）；若直接进入且无需求画像、或发现需求层仍有未澄清的冲突，先补做需求澄清（退回 `route-lookup` 或在本技能内补做），再继续方案。本技能的阻塞问题只管"怎么做"——实现方向、技术选型、拆解中的阻塞点。方案级阻塞问题一次只问一个，并给 2-3 个参考选项；非阻塞不确定性写入"假设"并继续。
- 方案只回答目标、范围、行为差异、实现方向、风险、验收标准与任务拆解。
- 所有文件与影响范围须基于用户需求、功能路由图与代码事实。
- **产出单一可选 artifact**：范围明确的中型任务产出一份 `spec.md`。
- 小而清晰的任务可直接在对话中完成，不落文件。
- 任务拆解采用**增量切片（slice）**：先定首批可验证切片，按需细化后续，避免一开始就穷尽式大计划，防止过早锁定决策。
- 不重写已确认的方案；不维护脱离实际代码的任务清单。

## 工作流程

1. 读取 `route-lookup` 输出、相关功能定位条目与必要代码上下文；确认其中包含已收敛的需求画像（目标 / 范围 / 边界 / 预期行为 / 约束）。若直接进入 spec 且无需求画像、或需求画像仍有未澄清冲突，先补做需求澄清再继续（见核心原则）。从 `route-debug` 进入时，同时读其调试摘要（根因、分歧点、修复方向、受影响文件、复现用例）作为方案输入。记录关键文件来源（路由图/扫描/不确定）。
2. 多代码库判定：判据见"跨工程工作区"小节——工作区规则中存在附库清单的显式声明才判为多代码库，否则按单工程处理。多代码库工作区中先确定任务涉及的库清单：涉及两个及以上库按跨库任务处理（建立各库任务目录与工作区协作文件）；只涉及一个库按单库流程处理（只在该库建任务目录，不建协作文件）；单工程跳过本步。
3. 判断是否存在**方案级**阻塞问题（实现方向、技术选型、拆解中的阻塞点）；有则按优先级一次只问一个，每个附 2-3 个参考选项。
4. 确认任务目标、范围内、范围外。
5. 对比当前行为与目标行为，给出推荐的实现方向。
6. 说明受影响的关键文件、风险、验收标准与验证方向。
7. **路由图影响作为一等交付物**：在 spec.md 的 `RouteSync` 小节列出预期新增/修改的具体路由条目（不只是 yes/no 占位），让路由图更新在方案阶段就可视。跨库任务时按库分别列出。
8. 任务拆解：按依赖顺序拆成带稳定 ID（`T1`/`T2`）的任务切片，每个任务列出文件范围、修改目标、验证方式；标注任务关系（强相关/弱相关/独立/冲突风险）；任务归属具体代码库时标注库。
9. 判断是否需要 `route-sync`，结论与预期条目一并写入 `RouteSync` 小节。
10. 产出：
   - 用户只想看方案时，停在方案产物。
   - 用户决定实现时：进入 `exec-plan`。

## 方案级阻塞问题格式

```md
先确认一个问题：{问题}

参考选项：
- A. ...
- B. ...
- C. ...（可选）
```

若选项无法覆盖用户意图，允许用户直接自定义。不得一次抛出多个阻塞问题。

## 任务关系

生成方案时只判定任务间关系，不决定执行者或执行方式。

- 强相关：顺序依赖、改同一核心文件、共享关键上下文、或需连续判断以保持一致。
- 弱相关：目标相关但文件边界较清晰；某任务完成后可独立处理。
- 无直接关系：文件与验证边界独立；只需最终集成检查。
- 冲突风险：多任务可能改同一文件、同一接口、同一测试入口或同一配置。

关系判定服务于执行阶段的排序、合并执行与冲突回避；不引入额外实现范围。

```md
# 方案：{spec_name}

## 目标
- ...

## 范围
- 内：...
- 外：...

## 假设
- 无 / ...

## 当前行为
- ...

## 目标行为
- ...

## 实现方向
- ...

## 受影响文件
- `path/to/file`（来源：路由图 / 扫描 / 不确定）：影响说明

## 风险
- 无 / ...

## 测试策略
- ...

## 验收标准
- ...

## 任务
- [ ] T1：...
  - 文件：...
  - 改动：...
  - 验证：...
  - 依赖：无 / ...

## 任务关系
- 强相关：无 / T1 + T2（理由）
- 弱相关：无 / ...
- 独立：无 / ...
- 冲突风险：无 / ...

## 跨库联动（跨库任务时）

## RouteSync
- 需要 route-sync：是 / 否 / 不确定
- 预期新增/修改条目：...（具体功能与业务域；跨库任务时按库分别列出）
```

## 跨工程工作区（多代码库）

触发条件：工作区规则（AGENTS.md、CLAUDE.md 等）中存在针对本工作区的显式声明——声明本工作区为多代码库共同开发，并附明确库清单（如前端、移动端、后端、网关）。使用说明、安装指引或引用文档中出现的相关措辞不算声明；无库清单的声明无效。二者缺一按单工程处理。

多代码库工作区中，任务按涉及库数量分流：**单库任务**（只涉及一个库）按单工程流程处理，只在该库根下建立任务目录，不建工作区协作文件；**跨库任务**（涉及两个及以上库）按下列规则处理：

- **各库独立管理**：每个涉及的代码库在自己的根下建立 `docs/routespec/yyyy-MM-dd-{spec_name}/`；`spec.md` 只写本库范围内的方案与任务拆解，可加"跨库联动"小节描述与其他库的接口与联动关系。
- **spec_name 统一命名**：同一跨库任务在所有涉及的库使用同一 `{spec_name}` 与同一日期，保证各库任务目录可互相关联。
- **工作区协作文件**：仅跨库任务在工作区根建立 `docs/routespec/yyyy-MM-dd-{spec_name}/collaboration.md`，记录跨库任务总体要求并关联各库任务目录，由跨库开发者自行维护。
- **跨工程协同文档**：跨库任务确认的持久协同约束、声明、契约（接口契约、数据结构、时序、事件、环境依赖等）沉淀到各库 `docs/routespec/cross-repo/` 下的主题文档（kebab-case 命名）。每份文档只写本库承担的部分，对端库的内容以文本引用（对端库名 + 其对应文档路径），不复制对端内容。与工作区协作文件的分工：协同文档是跨工程契约的按主题持久沉淀，协作文件是单个跨库任务的任务级关联。
- **执行与提交**：执行产物（`plan-fix{n}.md`、`unresolved-issues.md` 等）归各库自己的任务目录；代码提交在各库内分别进行。

collaboration.md 模板：

```md
# 跨库协作：{spec_name}

## 任务总体要求
- ...

## 关联任务目录
- {库}：`{库目录}/docs/routespec/yyyy-MM-dd-{spec_name}/`

## 跨库联动说明
- 接口契约 / 时序 / 环境依赖：...
```

## 输出要求与任务工作区

- **默认落地 `spec.md`**：写入任务目录 `docs/routespec/yyyy-MM-dd-{spec_name}/spec.md`。只有小而清晰的任务可直接在响应中给出方案摘要、不写文件。
- **任务目录即任务工作区**：该目录由本技能建立，贯穿 `spec → exec-plan → route-sync` 全流程。除 `spec.md` 外，任务过程中产生的相关产物都归集到同一目录，例如：
  - SQL 文件（迁移、查询、数据修正脚本等）
  - 需要输出的 API 文档、接口契约
  - 测试报告、验证输出
  - `plan-fix{n}.md`、`unresolved-issues.md`（exec-plan 产生）
  - 其它与该任务相关的临时或交付产物
  - 例外：跨库任务确认的持久协同契约沉淀到各库 `docs/routespec/cross-repo/`（见"跨工程工作区"小节），不归任务目录。
- 把这些产物放在同一任务目录，便于跨会话回溯、评审与归档；`spec.md` 作为该工作区的索引与方案主文档。
- 任务目录命名用当前日期；`spec_name` 用短 kebab-case；中文任务名转为稳定的英文或拼音摘要；目录已存在则追加 `-2`、`-3`。多代码库工作区按"跨工程工作区"小节处理：路径相对各库根，spec_name 跨库统一。
- 提交本任务变更时，在提交信息中记录任务目录位置（如 `Spec: docs/routespec/yyyy-MM-dd-{spec_name}`），由开发者惯用的提交技能或常规 git 流程完成。
- `spec.md` 是交给 `exec-plan` 的输入。
- 每个任务须有稳定任务 ID；任务关系、修复计划、执行摘要都引用这些 ID。
- 方案须包含任务关系判定（强相关/弱相关/独立/冲突风险）。
- 判断后续是否需要 `route-sync`。

## 退出条件

- 执行顺序已明确。
- 每个任务有文件范围与验证方式。
- 任务关系与冲突风险已判定。
- route-sync 需求已判定。
- 多代码库工作区中的任务：涉及库清单明确；跨库任务的各库任务目录与协作文件已建立、spec_name 已统一；单库任务只建该库任务目录、无协作文件。
- 下一步明确指向 `exec-plan` 或等待用户确认。

## 反模式

| 借口 | 现实 |
|---|---|
| "这太简单，不必做方案" | 简单功能也有边界情况和范围蔓延风险。2 分钟方案摘要能在编码前抓住它们。 |
| "我懂用户想要什么，直接开写" | 假设的意图是返工的头号来源。即便简短，也要先确认范围与行为。 |
| "我边实现边想方案" | 边设计边编码会把两种不同心态的活动搅在一起。分开更清晰。 |
| "需求很清楚，不必澄清" | 清楚的需求仍可能藏范围缺口、平台假设或冲突预期。显式确认范围内/外。 |
| "我一次把所有问题抛出来省时间" | 多问题齐抛会压垮用户，得到仓促、不完整的答案。一次一个阻塞问题更可靠。 |
| "route-lookup 找到了文件，我知道改什么了" | 知道改哪个文件 ≠ 知道改什么、为何改、风险多大。方案补上这一段。 |
| "我边走边想就行" | 无计划地实现会导致范围漂移、漏边界、验证不全。5 分钟方案省几小时返工。 |
| "任务相互依赖，没法分开计划" | 相互依赖正是任务关系要记录的——顺序依赖、共享文件、冲突风险。计划让依赖可见可控。 |
| "计划太小，不必用任务 ID" | 稳定 ID 支撑修复计划、审查引用与完成追踪。3 个任务也受益于 `T1`/`T2`/`T3`。 |
| "实现完再补计划" | 事后补的计划记录不了有用的东西，也无法防错。计划为实施服务，不是为留档。 |
| "任务关系很显然，跳过不写" | 对你显然，对执行子 agent（或未来的你）不然。写下来。 |

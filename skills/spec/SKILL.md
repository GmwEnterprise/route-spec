# 方案

把需求或已确认方向转化为清晰方案与可执行拆解，不直接写代码。

## 核心原则

- **阻塞问题聚焦方案层**：进入 spec 时先确认 `route-lookup` 是否已交付需求画像（目标 / 范围 / 边界 / 预期行为 / 约束）；若直接进入且无需求画像、或发现需求层仍有未澄清的冲突，先补做需求澄清（退回 `route-lookup` 或在本技能内补做），再继续方案。本技能的阻塞问题只管"怎么做"——实现方向、技术选型、拆解中的阻塞点。方案级阻塞问题一次只问一个，并给 2-3 个参考选项；非阻塞不确定性写入"假设"并继续。
- 方案只回答目标、范围、行为差异、实现方向、风险、验收标准与任务拆解。
- 所有文件与影响范围须基于用户需求、路由 wiki 查询结果与代码事实。
- **产出单一可选 artifact**：范围明确的中型任务产出一份 `spec.md`。
- 小而清晰的任务可直接在对话中完成，不落文件。
- 任务拆解采用**增量切片（slice）**：先定首批可验证切片，按需细化后续，避免一开始就穷尽式大计划，防止过早锁定决策。
- **设计约束作为评审基准**：显式记录不可破坏的接口、数据、权限、兼容性等契约；审查不得把约束明示允许的行为报为问题。
- **契约作为设计基准**：方案涉及跨端行为、数据格式、对外接口、模块边界等约束面时，先读在案契约（查询结果「涉及契约」→ `docs/integration/`）并纳入设计约束；属契约收录范围而无在案契约的列为待建契约；确需变更时先改契约再改代码，多端同改同验。
- **验证与评审随任务规划**：每个任务分别确定验证方式与是否启用 `code-reviewer`。
- 不重写已确认的方案；不维护脱离实际代码的任务清单。

## 工作流程

1. 读取 `route-lookup` 输出、命中页面的核心文件与必要代码上下文；「涉及契约」非空时先读对应 `docs/integration/` 文档；确认其中包含已收敛的需求画像（目标 / 范围 / 边界 / 预期行为 / 约束）。若直接进入 spec 且无需求画像、或需求画像仍有未澄清冲突，先补做需求澄清再继续（见核心原则）。从 `route-debug` 进入时，同时读其调试摘要（根因、分歧点、修复方向、受影响文件、复现用例）作为方案输入。记录关键文件来源（路由 wiki/扫描/不确定）。
2. 判断是否存在**方案级**阻塞问题（实现方向、技术选型、拆解中的阻塞点）；有则按优先级一次只问一个，每个附 2-3 个参考选项。
3. 确认任务目标、范围内、范围外。
4. 对比当前行为与目标行为，给出推荐的实现方向。
5. 说明受影响的关键文件、设计约束、风险、验收标准与验证方向；设计约束须引用在案契约，无契约覆盖且属其收录范围的列为待建契约。风险自查至少覆盖鉴权、不可逆数据操作、跨端契约变更与资源生命周期，未涉及的项目无需展开。
6. **路由 wiki 与契约影响作为一等交付物**：在 spec.md 的 `RouteSync 与契约影响` 小节列出预期新增/修改的页面（页面名与核心锚点，不只是 yes/no 占位）与契约影响（遵守 / 修订 / 新建），让 wiki 更新与契约变更在方案阶段就可视。
7. 任务拆解：按依赖顺序拆成带稳定 ID（`T1`/`T2`）的任务切片，每个任务列出文件范围、修改目标、验证方式与评审安排；标注任务关系（强相关/弱相关/独立/冲突风险）。单任务预计改动超过 10 个文件、跨 2 个以上业务域或叠加多个高风险面时，必须拆成可独立完成「编码 → 验证 → 按需评审」的小任务。
8. 判断是否需要 `route-sync` 与契约影响，结论一并写入 `RouteSync 与契约影响` 小节。
9. 产出：
   - 用户只想看方案时，停在方案产物。
   - 用户决定实现时：进入 `exec-plan`。

## 方案级阻塞问题格式

```md
先确认一个问题：{问题}

参考选项：
- A. ...
- B. ...
- C. ...（可选）
```

若选项无法覆盖用户意图，允许用户直接自定义。不得一次抛出多个阻塞问题。

## 任务关系

生成方案时只判定任务间关系，不决定执行者或执行方式。

- 强相关：顺序依赖、改同一核心文件、共享关键上下文、或需连续判断以保持一致。
- 弱相关：目标相关但文件边界较清晰；某任务完成后可独立处理。
- 无直接关系：文件与验证边界独立；只需最终集成检查。
- 冲突风险：多任务可能改同一文件、同一接口、同一测试入口或同一配置。

关系判定服务于执行阶段的排序、合并执行与冲突回避；不引入额外实现范围。

## 验证与评审计划

逐任务规划确定性验证与独立审查，不能把评审留到实现完成后临时决定：

- 验证方式优先选能覆盖该任务行为的单测、类型检查或 lint；启动装配、中间件连接与 Web 层改动按需补冒烟验证。
- 行为变更、跨模块、鉴权与数据敏感任务启用 `code-reviewer`；typo、纯配置、纯文档任务不启用。其余任务依据实际风险决定是否启用并说明理由。
- `spec.md` 的「设计约束」与「风险」是审查输入，「验证与评审计划」记录各任务的验证与评审安排。

## 输出要求与任务工作区

- **默认落地 `spec.md`**：写入任务目录 `docs/routespec/yyyy-MM-dd-{spec_name}/spec.md`。只有小而清晰的任务可直接在响应中给出方案摘要、不写文件。
- **任务目录即任务工作区**：该目录由本技能建立，贯穿 `spec → exec-plan → route-sync` 全流程。除 `spec.md` 外，任务过程中产生的相关产物都归集到同一目录，例如：
  - SQL 文件（迁移、查询、数据修正脚本等）
  - 需要输出的 API 文档、接口契约
  - 测试报告、验证输出
  - `plan-fix{n}.md`、`unresolved-issues.md`、`review{n}.md`（exec-plan 产生）
  - 其它与该任务相关的临时或交付产物
  - 例外：契约文档落 `docs/integration/`（唯一权威文档），不归任务目录，任务档案只留引用。
- 把这些产物放在同一任务目录，便于跨会话回溯、评审与归档；`spec.md` 作为该工作区的索引与方案主文档。
- 任务目录命名用当前日期；`spec_name` 用短 kebab-case；中文任务名转为稳定的英文或拼音摘要；目录已存在则追加 `-2`、`-3`。
- 提交本任务变更时，在提交信息中记录任务目录位置（如 `Spec: docs/routespec/yyyy-MM-dd-{spec_name}`），由开发者惯用的提交技能或常规 git 流程完成。
- `spec.md` 是交给 `exec-plan` 的输入。
- 每个任务须有稳定任务 ID；任务关系、修复计划、执行摘要都引用这些 ID。
- 方案须包含任务关系判定（强相关/弱相关/独立/冲突风险）。
- 判断后续是否需要 `route-sync`。

## 退出条件

- 执行顺序已明确。
- 每个任务有文件范围、验证方式与评审安排，且不超过拆解粒度门。
- 设计约束与方案级风险自查结论已记录，可作为评审基准。
- 任务关系与冲突风险已判定。
- RouteSync 与契约影响已判定。
- 下一步明确指向 `exec-plan` 或等待用户确认。

## 反模式

| 借口 | 现实 |
|---|---|
| "这太简单，不必做方案" | 简单功能也有边界情况和范围蔓延风险。2 分钟方案摘要能在编码前抓住它们。 |
| "我懂用户想要什么，直接开写" | 假设的意图是返工的头号来源。即便简短，也要先确认范围与行为。 |
| "我边实现边想方案" | 边设计边编码会把两种不同心态的活动搅在一起。分开更清晰。 |
| "需求很清楚，不必澄清" | 清楚的需求仍可能藏范围缺口、平台假设或冲突预期。显式确认范围内/外。 |
| "我一次把所有问题抛出来省时间" | 多问题齐抛会压垮用户，得到仓促、不完整的答案。一次一个阻塞问题更可靠。 |
| "route-lookup 找到了文件，我知道改什么了" | 知道改哪个文件 ≠ 知道改什么、为何改、风险多大。方案补上这一段。 |
| "我边走边想就行" | 无计划地实现会导致范围漂移、漏边界、验证不全。5 分钟方案省几小时返工。 |
| "任务相互依赖，没法分开计划" | 相互依赖正是任务关系要记录的——顺序依赖、共享文件、冲突风险。计划让依赖可见可控。 |
| "计划太小，不必用任务 ID" | 稳定 ID 支撑修复计划、审查引用与完成追踪。3 个任务也受益于 `T1`/`T2`/`T3`。 |
| "实现完再补计划" | 事后补的计划记录不了有用的东西，也无法防错。计划为实施服务，不是为留档。 |
| "任务关系很显然，跳过不写" | 对你显然，对执行子 agent（或未来的你）不然。写下来。 |

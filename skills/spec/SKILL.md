# 方案

把需求或已确认方向转化为清晰方案与可执行拆解，不直接写代码。

## 核心原则

- 需求未收敛不做方案：先核对需求画像（目标 / 范围 / 边界 / 预期行为 / 约束），有空缺或冲突先按"盘问式澄清"问透。
- 方案只回答目标、范围、行为差异、实现方向、风险、验收标准与任务拆解。
- 所有文件与影响范围须基于用户需求、路由 wiki 查询结果与代码事实。
- 产出单一可选 artifact：范围明确的中型任务产出一份 `spec.md`；小而清晰的任务可直接在对话中完成，不落文件。
- 任务拆解采用增量切片：先定首批可验证切片，按需细化后续，不一开始就穷尽式大计划。
- 设计约束与在案契约是评审基准：约束明示允许的行为不得报为问题；属契约收录范围而无在案契约的列为待建契约；确需变更先契约后代码，多端同改同验。
- 验证与评审随任务规划，不留到实现后临时决定。
- 不重写已确认的方案；不维护脱离实际代码的任务清单。

## 盘问式澄清

开发者通常清楚业务场景，技术细节未必清晰；本技能的职责是把模糊处全部盘出来——宁可问透，不可猜着做。

触发：直接进入且无需求画像、画像关键维度空缺或相互冲突、方案推演中暴露新的需求层疑问。

- 盘问维度：目标与动机；具体业务场景（谁、在什么情况下、怎么触发）；边界（明确不做什么）；预期行为（正常 / 异常 / 并发 / 失败时各自期望）；验收标准；隐含假设。
- 每轮抛出一组相关问题（2-4 个），每个附参考选项或推荐答案；选项无法覆盖时允许自由作答。
- 技术细节用户不清楚时，不问开放式技术问题，改给带取舍说明的选项与推荐。
- 含糊回答（"差不多""随便""你定"）追问一次具体场景；用户仍放权则显式复述自己的理解请其确认，确认即视为收敛。
- 一轮下来无新信息、无冲突即收敛；收敛后的画像写入 spec.md 对应小节。

## 方案级阻塞问题

方案推演中"怎么做"的阻塞点（实现方向、技术选型、拆解依赖）：按优先级一次只问一个，附 2-3 个参考选项，格式：

```md
先确认一个问题：{问题}

参考选项：
- A. ...
- B. ...
- C. ...（可选）
```

非阻塞不确定性写入"假设"并继续，不得一次抛出多个阻塞问题。

## 工作流程

1. 读取 `route-lookup` 输出、命中页面的核心文件与必要代码上下文；「涉及契约」非空时先读对应 `docs/integration/` 文档；从 `route-debug` 进入时读其调试摘要（根因、分歧点、修复方向、受影响文件、复现用例）。需求画像未收敛时先盘问。
2. 确认任务目标、范围内、范围外；对比当前行为与目标行为，给出推荐的实现方向。
3. 说明受影响的关键文件、设计约束（引用在案契约或列待建）、风险、验收标准与验证方向。
4. 任务拆解：按依赖顺序拆成带稳定 ID（`T1`/`T2`）的任务切片，每个任务列出文件范围、修改目标、验证方式与评审安排，并标注任务关系；单任务预计改动超过 10 个文件、跨 2 个以上业务域或叠加多个高风险面时，必须拆成可独立完成「编码 → 验证 → 按需评审」的小任务。
5. 判定 RouteSync 与契约影响并写入 `RouteSync 与契约影响` 小节：预期新增/修改页面（页面名与核心锚点）与契约影响（遵守 / 修订 / 新建），不只是 yes/no 占位。
6. 产出：用户只想看方案时停在方案产物；用户决定实现时，已落 `spec.md` 的进入 `run-spec`，仅在对话中给出方案的小任务在会话内直接执行。

## 任务关系

只判定关系，不决定执行者或执行方式：

- 强相关：顺序依赖、改同一核心文件、共享关键上下文、或需连续判断保持一致。
- 弱相关：目标相关但文件边界清晰，可独立处理。
- 独立：文件与验证边界独立，只需最终集成检查。
- 冲突风险：多任务可能改同一文件、接口、测试入口或配置。

关系判定服务于执行阶段的排序、合并执行与冲突回避；不引入额外实现范围。

## 验证与评审计划

- 验证方式优先选能覆盖任务行为的单测、类型检查或 lint；启动装配、中间件连接与 Web 层改动按需补冒烟。
- 评审触发：行为变更、跨模块、鉴权与数据敏感任务启用 `code-reviewer`；typo、纯配置、纯文档不启用；其余按风险决定并说明理由。
- 「设计约束」「风险」「验证与评审计划」是 `run-spec` 执行与评审的输入。

## spec.md 格式

```md
# 方案：{spec_name}

## 目标
- ...

## 范围
- 内：...
- 外：...

## 假设
- 无 / ...

## 当前行为
- ...

## 目标行为
- ...

## 实现方向
- ...

## 设计约束
- 无 / 不可破坏的接口、数据、权限、兼容性等契约（引用 `docs/integration/...` 或列待建）：...

## 受影响文件
- `path/to/file`（来源：路由 wiki / 扫描 / 不确定）：影响说明

## 风险
- 无 / ...
- 方案级自查：鉴权、不可逆数据操作、跨端契约变更、资源生命周期

## 测试策略
- ...

## 验证与评审计划
- T1：单测 / 类型检查 / lint / 按需冒烟；code-reviewer：是 / 否（理由）

## 验收标准
- ...

## 任务
- [ ] T1：...
  - 文件：...
  - 改动：...
  - 验证：...
  - 评审：code-reviewer 是 / 否（理由）
  - 依赖：无 / ...

## 任务关系
- 强相关：无 / T1 + T2（理由）
- 弱相关：无 / ...
- 独立：无 / ...
- 冲突风险：无 / ...

## RouteSync 与契约影响
- 需要 route-sync：是 / 否 / 不确定
- 预期新增/修改页面：...（页面名与核心锚点）
- 契约影响：无 / 遵守（`docs/integration/...`）/ 修订（先契约后代码）/ 新建
```

## 任务工作区

- `spec.md` 写入 `docs/routespec/yyyy-MM-dd-{spec_name}/spec.md`。任务目录由本技能建立，贯穿 `spec → run-spec → route-sync` 全流程；任务产物（SQL、API 文档、测试报告、`plan-fix{n}.md`、`unresolved-issues.md`、`review{n}.md` 等）归集同目录，`spec.md` 是其索引与方案主文档。例外：契约文档落 `docs/integration/`（唯一权威），任务档案只留引用。
- 任务目录命名用当前日期；`spec_name` 用短 kebab-case，中文任务名转稳定的英文或拼音摘要；目录已存在则追加 `-2`、`-3`。
- 提交本任务变更时，提交信息记录任务目录位置（如 `Spec: docs/routespec/yyyy-MM-dd-{spec_name}`），由开发者惯用的提交技能或常规 git 流程完成。

## 退出条件

- 需求画像已收敛（含经盘问收敛），方案级阻塞问题已清零或转为假设。
- 每个任务有文件范围、验证方式与评审安排，粒度不超过拆解门；任务关系与冲突风险已判定。
- RouteSync 与契约影响已判定；下一步明确指向 `run-spec` 或等待用户确认。

## 反模式

| 借口 | 现实 |
|---|---|
| "这太简单，不必做方案" | 简单功能也有边界情况和范围蔓延风险。2 分钟方案摘要能在编码前抓住它们。 |
| "用户说的就是他要的，不必盘问" | 口述需求常藏边界缺口、平台假设与冲突预期；盘问一轮的成本远低于返工。 |
| "我边实现边想方案" | 边设计边编码会把两种不同心态的活动搅在一起。分开更清晰。 |
| "route-lookup 找到了文件，我知道改什么了" | 知道改哪个文件 ≠ 知道改什么、为何改、风险多大。方案补上这一段。 |
| "任务相互依赖，没法分开计划" | 相互依赖正是任务关系要记录的。计划让依赖可见可控。 |
| "实现完再补计划" | 事后补的计划记录不了有用的东西，也无法防错。计划为实施服务，不是为留档。 |
